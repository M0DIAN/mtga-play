# 对局提速

目标是减少两次操作之间的重复工作，同时保留观察、合法性判断和结果证据。不要为了赶时间跳过局势变化或把未经检查的多步操作串起来。

## 开局前准备

- 在点击开始前完成牌表/规则读取、条件产费核对、常用组件关系和 UI helper 初始化。只加载当前套牌需要的参考。已知牌在局内按 ID 查必要字段，不重复输出整个数据库记录。
- 为当前牌表准备简短路线：可接受起手、前几回合主要展开、去除/牺牲优先级、引擎触发、致命计算注意点。路线是候选方案，抓牌或场面变化后调整。当前神器套牌可用 [已整理的组件关系](artifact-deck.md)。
- 在开始按钮输入前记录 `arena.note({type:"match_start", ...})`。先完成耗时的离线准备，起始事件才能主要反映实际对局时间。

## 局内循环

- 开局前启动 [实时日志状态](log-state.md)，局内先读简洁状态和新鲜度。用服务器占卜、堆叠及区域变化确认逻辑效果；当前GUI输入仍按computer-use立即刷新，但不再为已被日志明确确认的效果重复截图或逐张识牌。缺口后按字段补看，不把部分状态当作完整输入。
- 协调器快速流程使用 `presentation: 'compact'`，重复牌张按 `card_ref` 查同包目录；必要规则按 `details` 的有界路径取完整内容。`act()` 已刷新并返回截图；仅在双侧状态采样支持有效 `candidate_token/frame_reuse` 时，检查该全图后显式绑定下一步，省去额外 `observe()`。动画未完成、状态变化、预算到期、窗口变化、外部输入或关键区域不清楚时再观察。局部查看可用当前帧只读 PNG 裁剪，不能代替全图或产生新绑定。
- 本机第三局中，输入后立即返回的截图经常早于客户端重绘。若日志已确认提交而画面仍旧，先等相关日志状态/请求到达，再只补一次观察；不要把旧帧当作点击失败而重发输入。日志到达也不代表客户端动画完成，新的控件仍须从当前返回画面定位。
- 只需核对结算时先读简洁日志，不把每次日志轮询都绑定 `observe()`。等待使用相关请求编号或游戏状态变化作为条件，旧的“仍是我方决定”不能表示新控件已出现。需要新坐标才补观察；目标重试可使用 ui-play 的 `expected_request` 防止旧请求输入。不要批量输出全场对象来处理单个确认按钮。
- 调用只读等待可用 `arena.waitForProgress`（参数见ui-play）；调用前保存输入前的 `match_key/game_state_id/request.type/request.msg_id`，等待本次动作相关的预期效果或请求改变；保留时限，超时则报告未确认，再用画面诊断。原状态仍是我方决定时不能立即返回。等待只读取投影日志，不包含输入或截图，也不覆盖此前定位坐标绑定的请求。日志变化只是观察时机的依据，不保证重绘完成；若新帧仍在动画，继续有界等待，不能改称动作失败。
- 协调器用 `confirm({..., next:true})` 将已经检查的上一帧效果与下一决策读取合并；它只记账/读状态，下一输入仍须模型显式绑定。底层 [界面操作](ui-play.md) 的 `previousEffect` 仍可把已检查的旧效果随一个新输入记录。返回新图的同一工具调用不得确认该新图，下一次输入后仍立即刷新并停下来检查。
- 简单落地、明确的阶段推进、已核对过的选目标/确认按钮，用可见状态变化、意图及一句依据即可。不要每次重述整场计划、所有规则或全部候选。新卡、致命/防致命、阻挡、多重触发、支付与牺牲取舍需要更完整的计算。
- 每个我方回合首次决策记录简洁状态与当回合计划；后续记录变化。重要数量与区域不确定时明确标注。赛后重建样本的决策前状态时，只能使用该时点之前已观察到的信息。
- 选择牺牲、目标、攻击者前一次想清当前语义动作的后续候选，但每个输入都按最新画面重新定位。重复失败两次就诊断或改用有证据的替代方式，避免继续试同一操作。
- 生命、阻挡者与攻防确认后若已有致命线路，优先结束战斗；额外操作仅在提高实际成功率时继续。保留动态神器计数与离场重算。
- 局内仅写动作事件和必要纠错。完整复盘、训练格式、规则验证、skill 迭代放到对局结束后。持续工作时每约一分钟向用户说明有意义的进展，避免逐点击播报。

## 测量与比较

helper 自动记录输入调用、截图调用及从上一截图返回到下一次动作的间隔。`since_capture_ms` 包括看图、分析、工具往返及其它等待，不能当作纯模型思考时间。`action_cycle_ms` 包含输入、截图与前置记录，各指标存在重叠，不可相加。没有新指标的旧日志只分析事件时间戳，不把缺失值当作零。

v0.4.5 的协调器捕获包含两侧只读状态采样，`capture_ms` 包含这两次读取及可选窗口恢复，不能当成纯截图 API 时间；`since_capture_ms` 从实际 `get_window_state` 返回起算，因此包括截图后的采样和后续调度。`session_frame_use.reused_input_refresh` 只表示复用已捕获的当前候选，不证明已节省多少秒。比较时保留全部额外观察、失败、恢复与长尾。

v0.4 优先读取报告的 `captures.unique_count`、`input_refresh_count` 与 `extra_observe_count`；它们按 `controller_id/generation` 识别同一截图，回退 observation/execution 只算一次输入刷新。旧记录无法唯一对应时总数为 null，并保留已确认下限与覆盖原因。`raw_observation_event_count` 是原始行数，旧 `standalone_observation_count` 仅为它的兼容别名，不能当作去重后的额外截图数。分布的 P95 使用 nearest-rank，即排序后第 `ceil(0.95*n)` 项；保留样本量和缺失指标说明，小样本不用于稳定性能结论。

赛后运行：

```powershell
python -B -X utf8 <skill>/scripts/match_timing.py --session <session> --report <new-report.json>
```

以 `match_start` 到第一个 `game_result` 为范围；没有起始事件时默认从第一条 gameplay 决策开始，可能漏掉载入。旧局可显式指定 `--start-seq`。报告不会覆盖旧文件，也不会把未记录结果的会话标记为已完成。胜利记录可能晚于胜利画面，不能据此精确测量动画时间。

比较总时长、回合数、决策数、每动作的操作间隔、输入/截图耗时、额外观察数及恢复操作数。对手、回合数与局势复杂度不同会影响结果；没有新对局时只报告代码和离线验证，不声称实测已提速。
