# 实时对局主线与首批任务

## 目标与默认口径

让 Codex 接管实时对局，依据场面变化及时判断，快速完成输入，在原计划失效时改变打法。评估观察、决策、操作和恢复的完整过程。

首阶段固定当前 Windows 电脑、已经核对的分辨率、用户当前套牌与 Sparky 模式；每次真实对局的模式和局数以当次请求为准。仓库开发不自行启动比赛。身份、请求、连续性与画面定位分别核对；只使用当时合法可见的信息。

保留现有增量日志、规则资料与单步后端。没有新决策时在程序中等待；出现新选择时交给模型；模型返回过期结果时拒绝输入。语义动作不预存未来布局的坐标，输入成功与游戏效果确认分开记录。

## 首批任务：v0.4.0

### R1 — 统一状态与执行判断

**目标：** 读取状态和发送输入时使用一致的有效性规则，减少错误放行和正常等待时的无效回退。

**方案：** 区分监听心跳、已读到日志末尾、成功应用的状态、当前请求和本方决定权。正常等待同一受支持请求时，不单以最后游戏事件年龄判失效。未知必要状态保留缺口，不能通过新的消息时间恢复旧状态。Python 与 JavaScript 使用共享合成用例验证一致性。

**验收：** 过期心跳、未追上日志、请求不匹配和未支持请求均不得输入；健康等待仍可决策；异常状态只有有效新基线才能恢复。默认简报保留已有动态异能及完整计数标记。

**排除：** 猜测尚无真实样本的阻挡协议、完整规则引擎、进程内存读取。

### R2 — 持续会话与行动意图

**目标：** 将反复组织状态、时限、帧绑定和操作记录的工作固化到会话对象。

**依赖：** R1；沿用既有 `arena_ui` 单步输入接口。

**方案：** 有界等待新决策；以玩家可见状态生成 token；心跳不触发新推理，关键状态与请求变化使旧 token 失效。模型在检查画面后显式绑定当前帧与行动意图。控制器记录当前步骤和预期效果，操作后要求实际核验。换局、停止监听和超时取消旧步骤。

**验收：** 同一状态不重复生成决策；同请求下的动态异能或场面变化能触发重评；迟到结果、旧帧、已自动提交的请求不能继续点击；每次输入后只有一次自动刷新且效果初始未确认。所有行为以 mock 和有界文件监听验证。

**排除：** 自动后台模型调用、未实现的通用视觉定位、固定坐标批量点击、声称已完整接管真实客户端。

### R3 — 完整耗时口径与并行 CI

**目标：** 可准确判断改动有没有减少重复观察和长时间停顿。

**依赖：** 可与 R1/R2 并行，最终对集成候选验证。

**方案：** 以 controller_id 和 generation 区分截图；对回退重复记录去重；旧记录不能唯一辨认时输出未知或覆盖说明。保留总耗时、原始指标和缺失数，增加分位数。建立 Python、JavaScript、Windows 三项并行检查，Windows 只运行无输入轨迹测试。

**验收：** 同一输入后的 observation/execution 只计一张截图；不同控制器相同代数不合并；缺失时长不当零；现有回归继续通过。比较时必须包含恢复和等待。

**排除：** 用纯鼠标移动时间代替整个选择耗时、用不同对局直接估计因果提速率。

## 后续优先次序

1. **真实客户端接入验证。** 在本机依次检验启动、稳定等待、施放、选择、自动提交和结束；保存当前版本与最小脱敏证据。以此决定具体瓶颈，不先承诺秒级响应。
2. **有限的语义执行。** 为已验证界面实现“指定牌或控件 → 当前位置”的映射，逐步接续支付、选目标和占卜；使用实际阻挡与本地选择样本补请求语义。缺少样本时保持视觉回退。
3. **套牌战术计算。** 从神器数量、限制产费、牺牲和战斗计算开始，给模型提供少量可核对候选；出现未知规则时保留不确定性。
4. **决策预算与策略比较。** 在相同局面和执行后端上比较响应时间、有效动作率与关键错误，再决定是否需要不同模型或学习方法。

## 交付与验收门槛

功能变更须有直接相关的回归和独立复核，使用精确候选版本。CI 通过表示代码检查通过；真实操作通过、规则判断正确、策略有效分别报告。主线文档、代码与验证结果在同一 PR 内可审查，遵循用户当次授权推进提交、推送与合并。
